LCM は、記憶をニューラルネットワークの重みから切り離し、複数の数学的構造「格子」に注入する認知アーキテクチャです。**6 種類の専門化された格子コードブック** に異なるタイプの知識を格納し、非常に軽量な線形注意エンコーダが検索を担当し、**純粋な C で実装されたゼロパラメータ推論エンジン** が多段階の認知操作を実行します。すべての安全上重要な特性は **Z3 形式検証** により証明されています。

> 従来の Transformer は 3 つの本質的な制約に直面しています：より多くの知識を格納するにはパラメータを増やす必要がある（スケーリングの呪い）、インクリメンタル学習で古い知識が上書きされる（忘却の呪い）、推論プロセスが追跡不可能である（ブラックボックスの呪い）。LCM は記憶と推論をアーキテクチャレベルで分離することで、これらのボトルネックを根本的に突破します。

> **AI 支援声明**：本モデルの設計、実装、および推論プロセスでは、AI ツール（DeepSeek を含む）を支援として使用し、アーキテクチャ設計、コード作成、形式検証、ドキュメント作成において推論サポートを提供しています。

## 6 つの記憶格子

各格子は異なる数学的性質を持ち、特定の認知記憶を担当します：

| 格子 | 数学的タイプ | 担当 | コードブック更新 |
|-----|------------|------|----------------|
| **双曲残差階層格子** | Poincaré HRQ + SimVQ | 階層的概念記憶（意味階層） | 純勾配 |
| **ロバスト疎格子** | 標準 VQ + EMA + ソフト閾値縮小 | 稀なイベントと例外 | EMA + 特徴プールリセット |
| **残差低ランク格子** | IRVQ + 共有基底 | 抽象的なルールとパターン | 純勾配 |
| **双曲多様体格** | HyperVQ + 接空間 | 連続的な変化と文脈依存性 | EMA + 勾配 |
| **バインディング格子** | HRR 複素ベクトルバインディング | 関係の結合と連想記憶 | EMA + 勾配 |
| **二重コードブック対比格子** | DualVC + InfoNCE | 精細な区別と境界 | 純勾配 + 特徴プール |

**クロス層バインディング**：バインディング格子の 3 層キーコードブック × 3 層値コードブック = **9 対の HRR バインディング** により、多層的な関連性を捕捉します。

**共有基底**：低ランク格子の共有基底行列 `V` は、同時にバインディング格子に射影空間を提供し、パラメータを削減するとともに格子間の一貫性を強化します。

## ゼロパラメータ推論エンジン

推論エンジンは純粋な C99 で実装され、**学習可能なパラメータを一切含まない**動的データフローコンピュータです：

- **距離ルーティング**：入力と各格子コードブックとの距離が、どの操作を活性化するかを決定
- **プリミティブ集合**：検索、バインディング、低ランク変換、接空間スライディングなどの決定的数学操作
- **動的 DAG**：各ステップで入力内容に応じて距離ルーティングが動的に計算グラフを構築
- **マクロループ**：収束まで多段階推論を実行。収束判定は隣接ステップ間の `z` の変化量が閾値未満であること

コンパイル時次元定数 `LCM_D` により、すべての配列が固定サイズとなり、動的割り当ては行われません。

## 安全体系

LCM の安全体系は、優先度の高い順に 3 つの独立したサブシステムから構成されます：

| 層 | モジュール | 責務 | 更新方法 |
|---|----------|------|---------|
| 1 | **危険格子** `Λ_danger` | 推論状態に危険なパターンが存在するかを継続的に監視 | 永久凍結 |
| 2 | **全局価値格子** `Λ_gvalue` | アシモフの三原則（第零法則を含む）の数学的埋め込み | 永久凍結 |
| 3 | **外部検証プログラム** | 一貫性チェックと競合検出 | 読み取り専用 |

**ハード割り込み原則**：論理的矛盾が検出された場合、直ちに推論を停止し明確な警告を発します。迂回、バックトラック、自己修復は試みません。

すべての安全契約は Z3 SMT ソルバーによる形式検証を経ています（105 件の証明がすべて成立）。

```bash
pip install jax jaxlib numpy tokenizers

pip install cython && python lcm.py build
# C 推理引擎
cd infer && make LCM_D=256
```

```bash
# 文本 → BPE tokenizer → uint16 mmap
python lcm.py preprocess --input data.txt --tokenizer data/tokenizer.json --output data/tokens.dat

# 带启发式规则的数据清洗
python lcm.py clean --input raw/ --output clean/ --langid --dedup
```

### 学習

```bash
# Stage 1：训练解码器（语言模型头）
python lcm.py -d data/tokens.dat -b 16 -s 512 -dm 256 --steps 100000 --stage 1

# Stage 2：训练编码器 + 码本（冻结解码器）
python lcm.py -d data/tokens.dat --stage 2 -L checkpoints/lm_final.pkl

# Stage 3：联合微调
python lcm.py -d data/tokens.dat --stage 3 --resume checkpoints/memory_final
```

### インタラクティブ生成

```bash
python lcm.py -i checkpoints/step_10000 --max_new 128 --temp 0.7
python lcm.py -i checkpoints/step_10000 --loop     # 认知 DAG 循环模式
python lcm.py -i checkpoints/step_10000 --causal   # + 因果主体
python lcm.py -i checkpoints/step_10000 --obs      # + 自观察日志
```

## 3 段階学習

**現在の学習プロセス：認知学習（`cog_train.py`）がメインプロセス——認知システム全体（エンコーダ + 6 コードブック + W_out + 認知ループ）を訓練し、コードブックの更新も含みます。記憶学習（`train_memory.py`）は補助プロセスで、デプロイ後にコードブックを独立して更新するためのものです（継続学習）。両者は補完的であり、相互に排他的ではありません。**

以下の表は旧3段階スキームのもので、段階1のみが廃止されています：

| 段階 | 学習内容 | 凍結部分 | 損失 |
|-----|---------|---------|------|
| **1. LM 事前学習（歴史）** | デコーダ（生成ヘッド） | — | 言語モデリング交差エントロピー |
| **2. 記憶学習** | エンコーダ + 6 格子コードブック | デコーダ | VQ + 対比 + 直交 |
| **3. 結合ファインチューニング** | すべて（オプション） | — | すべての損失 |

この分離設計により、コードブックは推論デプロイ後も（`train_memory.py` を通じて）**更新を継続**でき、デコーダの言語能力に影響を与えません。真の継続学習を実現します。

### 勾配と EMA のハイブリッド管理

| 格子 | 更新方法 |
|-----|---------|
| 階層格子 / 低ランク格子 / 対比格子 / ルーティング格子 | 純勾配（AdamW） |
| 疎格子 / 多様体格 / バインディング格子 | EMA + 勾配の組み合わせ |
| 全局価値格子 / 危険格子 | 永久凍結 |

すべての格子の順伝搬には straight-through estimator (STE) を使用し、勾配流を維持します。

## 形式検証

LCM の形式検証は、Python 学習コードと C 推論エンジンの両方をカバーし、単一のテストパスではなく**すべての可能な入力**に対して安全上重要な特性が成立することを保証します。

| 境界条件 | 16 | 閾値/ゼロ値/極限 |
| 線形注意 | 7 | φ(x)>0 が恒成立 |
| GLU | 5 | 数値安定性 |
| 直交損失 | 6 | 非負 + 直交 ⇔ ゼロ |
| ポアンカレ/LFQ | 7 | 双曲計量の有界性 |

### C 側：Frama-C ACSL + 実行時契約

C 推論エンジンは二重の形式化手段を使用します：

**① Frama-C ACSL 注釈**（`/*@ assert ... */`）

关键数值计算点嵌入 ACSL 断言，可通过 Frama-C 静态证明：

```c
/* hyp.c — 庞加莱双曲运算 */
/*@ assert denom > 0.0f; */    /* 分母恒正（无除零） */
/*@ assert arg >= 1.0f; */     /* arcosh 定义域检查 */
/*@ assert t < 1.0f; */        /* atanh 定义域：|t| < 1 */

/* lattice.c — 格检索 */
/*@ assert best_idx >= 0 && best_idx < mem->M; */  /* 码本边界安全 */
/*@ assert mag > 0.0f; */                          /* FFT 幅值恒正 */

/* engine.c — 推理引擎 */
/*@ assert diff >= 0.0f; */    /* 收敛判据非负 */
/*@ assert w > 0.0f; */        /* 融合权重恒正 */
```

**② REQUIRE/ENSURE 設計契約**（実行時アサーション）

关键安全模块使用 DbC 风格的前置/后置条件：

```c
#define REQUIRE(cond) assert(cond)
#define ENSURE(cond)  assert(cond)

void gvalue_init(gvalue_t* gv, ...) {
    REQUIRE(gv != NULL && C_pos != NULL);
    REQUIRE(D == LCM_D);
    // ...
    ENSURE(gv->integrity_hash[0] != '\0');
}
```

**③ ビルドターゲット**

```bash
cd infer
make contracts    # 启用 -DLCM_USE_CONTRACTS，运行时验证契约
make test         # 单元测试（DEBUG + 契约）
make debug        # DEBUG + 契约构建
```

**④ スレッド安全性の保証**（構造レベルの不変条件）

- `static` / グローバルな可変状態なし
- すべてのメモリは呼び出し側が所有（caller-owns, callee-operates）
- 固定サイズ配列、動的割り当てなし
- 純粋な C99、外部依存なし（`libm` のみ）

これらの不変条件は C コード構造によって保証され、Z3 側（P16 決定性証明）は対応する数学モデルが純関数であることを検証します。

## ハードウェア効率

| 指標 | 数値 |
|-----|------|
| 総パラメータ数 | ~12M（埋め込み含む） |
| FP16 重み | ~24MB |
| 学習 GPU メモリ | < 1.5GB |
| 推論実行時 | ゼロパラメータ（コードブック参照のみ） |
| 対応ハードウェア | **4GB コンシューマ GPU** |

線形注意の `O(N d²)` 計算量は、従来の注意機構における `N×N` 行列格納を回避し、長いシーケンスの学習をコンシューマグレードのハードウェアで可能にします。

### 推論速度の理論解析

**論理連鎖推論**（d=256, H=4, N=512, L_enc=2, ゼロパラメータ動的 DAG エンジン）：

1. **エンコーダ（インクリメンタル）**：初期実装では毎ステップでスライディングウィンドウ全体を再計算 `O(N·d²)`。インクリメンタル更新により毎ステップ `O(d²)` — **1/512 に削減**。JAX は小規模行列演算を少数の CUDA カーネルに融合し、カーネル起動オーバーヘッド（~10μs）が計算自体を支配します。GPU ~25-50μs、CPU ~50-100μs。

2. **C 推論エンジン（マクロループ + 動的 DAG）**：これが支配的なコストです。各マクロステップ：
   - `build_dag()` が `z` と各格子コードブックとの距離を計算し、活性化するプリミティブを動的に選択（距離が閾値未満の格子のみ DAG ノードとして追加；トポロジは毎ステップ変化）
   - 4 層 DAG を実行：retrieve（並列）→ bind → unbind → fusion。シングルスレッド C では各層内のプリミティブが順次実行
   - 融合後に安全性チェック（危険格子 + 全局価値格子）を実行
   
   マクロループは **3〜5 ステップ** 繰り返され、二重収束条件を確認：`||Δz|| < tol` **かつ** 融合重みエントロピー `H({w_i}) < entropy_threshold`。各マクロステップは新しい DAG を構築 — 計算グラフは固定ではなく、現在の `z` に応じて動的に適応します。
   
   単一コードブックの距離スキャンは、活性化された格子あたり ~50-90μs（L3 キャッシュ常駐、メモリ帯域律速）。各ステップで典型的に 3-6 個の格子が活性化され、グラフ構築、bind/unbind、融合、安全チェックを加えると、各マクロステップは ~300-600μs。3-5 ステップで合計 **~1.0-3.0ms**。この部分は GPU モードに関係なく常に CPU 上で実行されます。コードブックデータはホストメモリに存在するためです。

3. **デコーダ + サンプリング**：線形注意 + GLU（JAX）。GPU ~20-40μs、CPU ~50-150μs。

4. **JAX↔C ブリッジ**：`z` は ctypes を介して JAX 配列と C ポインタ間を行き来します（トークンあたり 2 回）：**~20-60μs**。

5. **Python ループ**：フロー制御と状態管理：**~10-30μs**。

**最終推定**（トークンあたりのレイテンシ、単一推論、d=256）：

| 工程 | GPU | CPU |
|-----|-----|-----|
| インクリメンタルエンコーダ | 25-50μs | 50-100μs |
| JAX↔C ブリッジ（×2） | 20-60μs | — |
| C エンジン（3-5 マクロステップ × 動的 DAG） | 1,000-3,000μs | 1,000-3,000μs |
| デコーダ + サンプリング | 20-40μs | 50-150μs |
| Python ループ | 10-30μs | 10-30μs |
| **トークンあたり合計** | **1,075-3,180μs** | **1,110-3,280μs** |
| **スループット** | **310-930 tok/s** | **300-900 tok/s** |

C エンジンのマクロループが全体の ~80-90% を占めます。コードブックの距離計算はメモリ帯域律速であり、GPU モードに関わらず CPU 上で実行されるため、単一推論では GPU と CPU のスループットは同程度です。複数クエリをバッチ処理すればエンコーダ/デコーダの GPU 利用率は向上しますが、シーケンスあたりの C エンジンコストはバッチ次元で逓減しません。

> これらは単一推論の理論推定値です。現在の Python + ctypes ブリッジ実装では追加のオーバーヘッドが発生する可能性があります。学習スループットは 3,000-5,000 tok/s（B=16, N=512, GPU）で、データローディングと optimizer 更新に制限されます。距離計算を GPU カーネルにオフロードすれば理論的には検索時間を短縮できますが、動的 DAG の制御フロー、bind/unbind、fusion、収束判定は本質的に GPU 実行に適しておらず、各マクロステップで最低 1 回の PCIe ラウンドトリップ（z → GPU、距離 → CPU）も必要です。単一推論では効果は限定的です。
